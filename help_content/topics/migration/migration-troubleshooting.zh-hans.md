---
title: 迁移故障排除
---

大多数迁移都能顺利完成，但连接会失败，导入会超时，偶尔运行会在中途停止。本主题涵盖诊断失败连接、在导入运行时阅读进度日志，以及——最重要的是——一旦出现问题时您真正拥有的选项，包括 Retry（重试）、Cancel（取消）和 Rollback（回滚）实际上做了什么。

## 第 2 步连接失败

**Test connection before proceeding**（在继续前测试连接）复选框默认是启用的，这是您的第一个诊断工具——它在您提交其余向导步骤之前，会验证凭据与源平台的匹配性。如果失败，错误信息通常指向以下问题之一：

- **WooCommerce** — Store URL 缺少 `https://` 或带有尾部路径段；Consumer Key/Secret 错误或重新生成；或在 **WooCommerce > Settings > Advanced > REST API** 中创建的 REST API 密钥没有 **Read** 权限。
- **Shopify** — Store Domain 不是 `yourstore.myshopify.com` 格式；Client ID/Secret 来自错误的应用；或者，最常见的问题是应用在 Dev Dashboard 中创建但从未实际 **安装** ——创建应用版本是不够的，您需要自定义分发链接并点击 **Install**。如果应用的权限范围中没有包含 `read_products`、`read_customers` 或 `read_orders`，Spwig 也会发出警告。
- **Magento 2** — Store URL 指向的是商店前端而非 API 根路径，或一个已创建但未激活的集成令牌 (**Save > Activate > Allow**)。
- **SSL 问题** — 过期、自签名或配置错误的证书会在验证凭据之前导致连接失败，显示为通用错误而非认证错误。如果凭据看起来正确，请检查证书。

在每次修复后重新运行连接测试，而不是一次性更改多个凭据——这有助于隔离哪个凭据是错误的。

## 在第 5 步阅读实时日志

在导入运行时，第 5 步会显示实时活动日志。

点击 **显示详细信息**，将其展开为单独的条目 —— 级别和消息 —— 而不是仅仅显示当前步骤的摘要。

如果进度看起来停滞不前，这是查看情况的最快方式：某种数据类型的大量“已跳过”条目通常只是意味着“跳过现有条目”功能按预期工作，而不是说有任何东西卡住了。

日志视图仅显示 **最近的 500 条条目**，因此在进行大规模迁移时，最早的条目会在导入仍在运行时滚动出视图。如果在某种数据类型完成之后需要完整的日志，请改用结果页面上的 **下载日志** —— 它没有此类限制。

## 迁移失败实际上意味着什么

这是在迁移失败时最重要的事情要理解。

当迁移失败时，完成页面会明确告诉你发生了什么：错误发生前导入的项目仍然保留在你的商店中，没有任何内容会被自动删除，解决问题并重新运行导入将跳过那些第一次已经导入的内容。请按字面意思理解这一点。导入过程中的任何步骤都不会在可以作为一个单元回滚的数据库事务中运行 —— 在失败点之前成功导入的内容，如产品、分类、客户、订单等，都会以创建时的精确状态保留在你的商店中。失败的迁移是一个 **部分** 迁移，而不是未完成的迁移。

失败还会将任务标记为不再可回滚，因此 **回滚** 按钮在失败的 **导入** 上将不可用 —— 它只会在迁移完成后出现，或者在已完成迁移自身的回滚中途失败时再次出现，此时 Spwig 会再次提供该按钮，以便您重试。您最需要自动撤销的情况 —— 失败的导入 —— 恰恰仍然是按钮不会提供的那种情况。

因此，当迁移失败时：

1. **查看实际导入的内容**，使用已导入/跳过/失败的计数和下载的日志，构建出你店铺中实际导入的内容与未成功导入内容之间的对比。
2. **决定如何清理数据。** 对于少量的部分数据，可以手动查看并删除不需要的内容，通过常规的管理员列表视图进行操作。

对于更大或更混乱的部分导入，通常在重新开始之前自己清除已导入的数据会更快，而不是逐项核对。
3. **无论选择哪种清理路径，都重新运行并启用跳过已有商品选项** —— 这可以防止之前成功导入的数据在下一次运行时被重复导入。

## 重试

**重试** 会从头开始完全重新启动导入。它会清除任务之前的计数器和日志，并从头开始重新导入所有内容 —— 它 **不会** 从失败尝试停止的地方继续执行。请保持 **跳过已有商品** 选项启用，以确保第一次成功导入的商品在第二次运行时不会被重复导入。

如果迁移因达到 **4小时** 限制而停止，你看到的信息是准确的：再次运行导入会从头开始，并跳过之前已导入的商品，而不是从停止的地方继续执行。对于足够大以至于达到时间限制的店铺，反复重试整个导入过程很少能完成；相反，通过在第3步中选择更少的数据类型（例如一次运行商品，另一次运行订单）来减少每次运行的范围，进行多次较小的导入会更有效。

## 取消

**取消** 可用于正在运行的迁移，并会立即在仪表板中标记该任务为失败。它 **不会** 停止后台导入任务，该任务将继续运行并写入数据，直到自然停止。在你取消后，预计导入计数仍会继续上升一段时间 —— 在决定清理数据之前，让这些计数稳定下来，而不是基于你点击取消时的即时计数采取行动。

## 没有暂停或恢复功能


Spwig 不支持暂停正在进行中的迁移并在之后继续执行。

仪表板上的 **Resume**（恢复）按钮用于另一种情况：通过向导配置但从未开始执行的迁移。

它会重新打开向导，从你上次配置的位置继续 —— 与正在进行的运行无关。

## 回滚

> **警告：** 回滚是一个永久且具有破坏性的操作。在使用之前，请完整阅读本节内容。

回滚仅适用于 **已完成** 的迁移，也适用于之前回滚过程中失败的迁移（状态为 **回滚失败**），因此可以重新尝试回滚。它只会移除迁移本身创建的内容，而保留您当前商店依赖的任何内容：

- 一个已迁移的客户，如果在导入后已经下了真实订单，将 **保留** —— 他们的账户、地址、忠诚度历史和商店积分会保留在他们身上，且那个真实订单不会被修改。只有导入创建的订单会被移除。
- 一个已迁移的产品，如果仍被任何订单、捆绑包、礼品卡或配置器插槽引用，将 **保留**。其他客户的订单永远不会被修改 —— 回滚无法从不相关的订单中移除商品行项目，也不会让订单金额出现错误。
- 所有保留的内容都会以名称和数量的形式向您报告，并附带原因 —— 例如“1 个产品保留，仍被订单项目引用” —— 这样您可以清楚地知道哪些内容仍然存在以及原因。
- 由导入创建的联盟、佣金和付款 **会被移除**，以及导入创建的任何联盟账户。如果一个联盟与一个已存在的客户相关联，该客户会保留其账户；只有联盟记录会被移除。
- 忠诚度历史和商店积分会跟随客户：如果客户被移除，这些内容也会被移除；如果客户被保留，这些内容也会被保留。

它仍然 **不会** 移除由商店扩展创建的订阅计划、定价层级或预订资源 —— 这些内容在回滚后仍然存在，如果您不希望它们保留，需要手动清理。

在确认之前，确认页面会显示确切将被删除和保留的内容预览，这些内容是根据您的实时数据计算得出的 —— 点击 **是，回滚迁移** 之前请先阅读。

回滚操作将在后台运行，而不是在您的浏览器中运行，因此您可以安全地关闭标签页；在操作完成后，可以检查迁移的状态以查看实际删除和保留的内容报告。

由于回滚操作不再超出导入所创建的内容范围，因此它不再是一个仅限当天使用的工具 —— 无论自迁移以来经过了多长时间，迁移后的客户的真实订单和迁移后产品的实际销售记录都将受到保护。它仍然是对所删除行的永久性、破坏性操作，因此请慎重使用，而不是随意使用，并手动清理 Spwig 保留的您实际上并不需要的内容。

关于可用性：回滚按钮会在已完成迁移的摘要中保留，只要作业记录存在 —— 对于大多数平台来说，没有固定的截止日期。Magento 是例外，回滚功能在设定的时间窗口后将失效，因此如果您使用的是 Magento，请尽快决定是否需要回滚。作业记录不会按照任何计划被删除，因此除非您自己删除记录，否则迁移将可以无限期地回滚。

## 大型店铺策略和缓慢导入

对于规模较大的店铺，单次运行可能会面临 4 小时的限制：

- **在第 3 步中提高批次大小**（最多 100）— 更大的批次通常意味着更少的往返次数和更快的吞吐量。
- **按数据类型将迁移拆分为多次运行** —— 将类别和产品放在一次运行中，客户和订单放在后续运行中，而不是一次性全部运行。
- **在第一次运行之后的每次运行中，保持 Skip existing items 启用**，以避免重复运行时重复已成功的内容。
- **关闭 Import product images（导入产品图片）**。下载和处理每张图片通常是导致运行缓慢的最主要原因。



你可以单独为产品添加图片，也可以在其余数据准备就绪后，通过单独的CSV导入来添加图片。

## 提示

- **每次更改凭证后都要测试连接**，而不是只在最后测试一次 —— 这有助于确定哪个值是错误的。
- **不要假设失败的任务会自行清理** —— 在决定清理或重试之前，请检查商店中实际的内容。
- **每次重试时应保留跳过现有项目** —— 这是防止第二次处理时出现重复的唯一方法。
- **不要通过增加重试次数来对抗4小时的限制** —— 应该根据数据类型进行拆分。
- **确认前先阅读回滚预览** —— 它会明确说明将删除和保留的内容，并基于实时数据进行计算，因此不会有意外情况。
