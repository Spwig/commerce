---
title: 遷移問題排除
---

大多數遷移都能順利完成，但偶爾會出現連接失敗、導入超時，或在執行過程中突然中止的情況。本主題涵蓋如何診斷連接失敗、在導入過程中讀取進度日誌，以及最重要的——當出現問題時，您實際上有哪些選擇，包括 Retry（重試）、Cancel（取消）和 Rollback（回滾）實際上會做什麼。

## 第 2 步的連接失敗

**Test connection before proceeding**（在繼續之前測試連接）複選框預設是啟用的，這是您的第一個診斷步驟——它會在您提交整個向導之前，驗證憑證與來源平台的匹配性。如果測試失敗，錯誤訊息通常會指出以下問題之一：

- **WooCommerce** — 儲存 URL 缺少 `https://` 或包含尾部路徑片段；Consumer Key/Secret 輸入錯誤或重新生成；或在 **WooCommerce > Settings > Advanced > REST API** 中創建的 REST API 金鑰沒有 **Read** 權限。
- **Shopify** — 儲存域名格式不是 `yourstore.myshopify.com`；Client ID/Secret 來自錯誤的應用程式；或最常見的情況是應用程式是在開發儀表板中創建，但從未實際 **安裝** — 創建應用程式版本是不夠的，您需要自訂分發連結並點擊 **Install**。Spwig 也會在應用程式範圍中未包含 `read_products`、`read_customers` 或 `read_orders` 時發出警告。
- **Magento 2** — 儲存 URL 指向的是商店前端而非 API 根目錄，或是一個已建立但從未啟用的整合令牌 (**Save > Activate > Allow**)。
- **SSL 問題** — 過期、自簽名或配置錯誤的憑證會在驗證憑證之前就導致連接失敗，顯示為一般錯誤而非驗證錯誤。如果憑證看起來正確，請先檢查憑證。

在每次修復後重新執行連接測試，而不是一次更改多個憑證 — 這有助於確定哪個憑證有問題。

## 在第 5 步讀取即時日誌

在導入過程中，第 5 步會顯示即時活動日誌。

點擊 **顯示詳細資訊** 可將其展開為獨立項目 —— 級別和訊息 —— 而非僅顯示目前步驟的摘要。

如果進度看起來卡住了，這是查看情況最快的辦法：某種資料類型出現一整面牆的 "跳過" 項目，通常只是表示 "跳過現有項目" 功能運作正常，而不是說有任何東西卡住了。

日誌檢視器只顯示 **最近的 500 項記錄**，因此在進行大型資料遷移時，最早的一些記錄會在導入仍在進行時滾出視窗。如果在某種資料類型完成後需要完整的日誌，請改用結果頁面上的 **下載日誌** —— 它沒有這樣的限制。

## 失敗的遷移實際上意味著什麼

這是理解遷移失敗時最重要的事情。

當遷移失敗時，完成頁面會清楚地告訴你發生了什麼：錯誤發生前導入的項目仍然會留在你的商店中，沒有任何東西會自動被刪除，解決問題並重新運行導入將會跳過已經成功導入的項目。請務必認真對待這一點。導入過程中的任何步驟都不會在資料庫事務中執行，因此無法作為一個整體進行回滾 —— 在失敗點之前成功導入的項目，例如產品、分類、客戶、訂單，或工作已經處理的任何內容，都會以創建時的狀態完全保留在你的商店中。失敗的遷移是一次 **部分** 的遷移，而不是未完成的遷移。

失敗也會將工作標記為不再可回滾，因此 **回滾** 按鈕在失敗的 **導入** 上將不可用 — 它只會在遷移完成後出現，或者在已完成遷移本身的回滾中途失敗時再次出現，此時 Spwig 會再次提供該按鈕，讓您可以重試。您最需要自動撤銷的情況 — 失敗的導入 — 恰恰仍然是這個按鈕不會出現的情況。

因此，當遷移失敗時：

1. **審查實際導入的資料**，使用已導入/跳過/失敗的數量以及下載的日誌，來建立一個畫面，了解您商店中實際存在的資料與未能導入的資料之間的差異。
2. **決定如何清理資料。** 對於少量的部分資料，可以手動審查並透過正常的管理員列表視圖刪除不需要的資料。

對於較大或較混亂的部分導入資料，通常在重新開始之前自行清除導入的資料會更快，而不是逐一核對每個項目。
3. **無論選擇哪種清理路徑，都重新執行並啟用跳過現有項目** — 這可以防止已經成功導入的資料在下一次執行時被重複導入。

## 重試

**重試** 會從頭開始完全重新執行導入。它會清除作業的先前計數器和日誌，並從頭開始重新導入所有資料 — 它 **不會** 從上次失敗的執行中斷的地方繼續執行。請保持 **跳過現有項目** 啟用，這樣第一次已經導入的項目在第二次執行時就不會被重複導入。

如果遷移因為觸及 **4小時** 的限制而停止，您看到的訊息是正確的：重新執行導入會從頭開始，並跳過已經導入的項目，而不是從中斷的地方繼續執行。對於足夠大到觸及時間限制的商店，反覆重試整個導入很少能完成；相反地，請透過在步驟3中選擇較少的資料類型（例如一次導入產品，另一次導入訂單）來減少每次執行的範圍，並進行多次較小的執行。

## 取消

**取消** 可在正在執行的遷移上使用，並會立即在儀表板中將作業標記為失敗。它 **不會** 停止後台導入任務，後台任務會繼續執行，直到達到自然的停止點為止。在您取消後，預期導入的數量會持續增加一段時間 — 在決定要清理什麼之前，讓這些數量穩定下來，而不是根據您點擊取消時捕捉到的數量採取行動。

## 沒有暫停或恢復功能


Spwig 不支援暫停進行中的遷移並稍後重新啟動。

儀表板上的 **繼續** 按鈕適用於另一種情況：透過向導設定但從未開始的遷移。

它會重新打開向導，讓您從上次設定的位置繼續進行 — 與已經進行中的執行無關。

## 回滾

> **警告：** 回滾是一個永久且具破壞性的操作。請在使用前完整閱讀本節內容。

回滾僅適用於 **已完成** 的遷移，也適用於自身回滾曾經中途失敗的遷移（狀態為 **回滾失敗**），因此停滯的回滾可以重試。它只會刪除導入本身建立的內容，並保留您商店目前仍然依賴的一切：

- 一位已遷移的客戶，如果自導入以來下過真實訂單，會被 **保留** — 其帳戶、地址、忠誠度歷史和商店購物金都會保留，且該真實訂單不會被觸動。只有導入建立的訂單才會被刪除。
- 仍被任何訂單、組合包、禮品卡或配置器插槽引用的已遷移產品會被 **保留**。屬於其他客戶的訂單永遠不會被修改 — 回滾不會再從無關訂單中刪除訂單項目，也不會讓其總額出錯。
- 被保留的內容都會依名稱和數量回報給您，並說明原因 — 例如「保留了 1 項產品，仍被某個訂單項目引用」— 這樣您就能準確知道還留下了什麼以及原因。
- 導入建立的聯盟、佣金和付款 **會** 被刪除，導入建立的任何聯盟帳戶也會一併刪除。附屬於原本已存在客戶的聯盟，會保留該客戶的帳戶；只刪除聯盟記錄本身。
- 忠誠度歷史和商店購物金會跟隨客戶：客戶被刪除則一併刪除，客戶被保留則一併保留。

它仍然 **不會** 刪除由商店擴充功能建立的訂閱方案、定價層級或預訂資源 — 這些內容在回滾後依然存在，如果您不想保留，需要手動清理。

在您確認之前，確認頁面會顯示一份預覽，準確列出將被刪除和將被保留的內容，這是根據您的即時資料計算得出的 — 請在點擊 **是，回滾遷移** 之前閱讀它。之後回滾會在後台執行，而不是在您的瀏覽器中執行，因此關閉標籤頁是安全的；完成後請查看遷移的狀態，以取得實際刪除與保留內容的報告。

由於回滾不再波及導入建立範圍之外的內容，它不再是一個只能在當天使用的工具 — 無論距離遷移已經過去多久，已遷移客戶的真實訂單和已遷移產品的真實銷售記錄都會受到保護。它對自己確實刪除的資料列仍然是一項永久且具破壞性的操作，因此請謹慎使用，而非隨意操作，並手動清理任何 Spwig 保留下來但您實際上不想要的內容。

關於可用性：回滾按鈕會在已完成遷移的摘要頁面上顯示，只要工作記錄存在 — 對於大多數平台來說，沒有固定的截止日期。Magento 是例外，遷移後經過一段時間後將失去回滾功能，因此如果你使用的是 Magento，請迅速做出決定。工作記錄不會按照任何排程被移除，因此除非你自行刪除該記錄，否則遷移將無限期保持可回滾狀態。

## 大型商店策略和緩慢導入

對於規模足夠大的商店，單次運行可能面臨 4 小時的限制：

- **在步驟 3 中提高批次大小**（最多 100）— 更大的批次通常意味著更少的往返次數和更快的吞吐量。
- **按數據類型將遷移拆分到多個運行中** — 一次運行類別和產品，另一次運行客戶和訂單，而不是一次性全部運行。
- **在每次後續運行中保持 Skip existing items 啟用**，這樣重複運行不會重複已經成功的內容。
- **關閉 Import product images。** 下載和處理每張圖片通常是導致運行速度變慢的最主要因素。



您可以個別地為產品添加圖片，或者在其他數據已經就緒後，通過獨立的CSV導入來添加圖片。

## 小技巧

- **每次更改憑證後都應測試連接**，而不是僅在最後測試一次 —— 這樣可以隔離出哪個值是錯誤的。
- **不要假設失敗的任務會自行清理** —— 在決定清理或重試之前，請檢查商店中實際的內容。
- **重試時應保留跳過現有項目** —— 這是在第二次處理時防止重複的唯一方法。
- **不要通過增加重試次數來對抗4小時的限制** —— 而是根據數據類型進行拆分。
- **確認前請閱讀回滾預覽** — 它會準確說明將刪除什麼內容以及保留什麼內容，這些都是根據您的即時資料計算得出的，因此不會有任何意外。
